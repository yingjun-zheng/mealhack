# 服务端返回 success: true，但价格是错的

> 麦当劳 MCP 开发踩坑记 —— 一个"静默失败"，如何让 600 个参赛项目同时踩雷

---

## 一、先说说这个赛道有多挤

我参加了一个麦当劳的 AI 开发比赛。报名 Issue 已经到 1166 条，去重后大概 500~600 个项目。

翻了一遍排行榜前 100 名，主题分布是这样的：

- 预算/省钱助手：至少 20 个
- 热量/营养计算：10 个以上
- 点单推荐：一大堆
- 塔罗运势、MBTI、拼单、年度报告：各有若干

**也就是说，如果你现在去做"帮用户点麦当劳省钱"，你就是第 21 个。**

我翻了 MCP 的版本日志，看到一行字：

> 2026-06-16 1.0.5 支持**更换套餐内商品组合**、部分餐品特制

所有人都默认"套餐是一个固定商品"。但这个能力说明：**套餐其实是一个可替换的组合空间**。

而 `calculate-price` 这个接口——**不下单、不花钱、不占库存**——意味着这个空间可以被完整枚举并真实核价。

于是就做了一个东西：把套餐的所有合法组合算出来，输出价格-蛋白质的帕累托前沿。

一个麦辣鸡腿堡三件套，有 **154 种**合法组合（去掉缺营养数据的，实际分析 84 种）。实付区间从 32 元到 47 元，**差 15 块**。

这不是隐藏优惠，是一直摆在菜单上、但人脑在点餐的 30 秒里根本穷举不完的选择空间。

## 二、6 个坑，第 6 个最阴

下面这些全是真机联调跑出来的，不是我编的。

### 坑 1：`content[].text` 不是 JSON

MCP 返回的 `content[0].text` 经常是**「给 LLM 看的展示规则说明 + 原始 JSON」**拼在一起的混合文本：

```
每个门店的基本信息按单行展示：
- **门店名称**: data[].storeName
- **门店编号**: data[].storeCode
...
{"success":true,"code":200,"data":[{"storeCode":"3230251",...}]}
```

直接 `json.loads()` 必然失败。解法是扫描文本、按括号平衡提取出其中最大的合法 JSON 负载。

### 坑 2：两个接口的金额单位不一样

| 接口 | 字段 | 值 | 单位 |
|---|---|---|---|
| `query-meals` | `currentPrice` | `"33.5"` | **元**（还是字符串）|
| `calculate-price` | `data.price` | `3350` | **分** |

我一开始统一按"分"处理，结果套餐价变成 0.34 元，整个价格区间跑成了 -1.16 ~ 44。

**同一个服务商的两个接口，金额单位不统一。** 这种事不写进 schema 就永远是个雷。

### 坑 3：`beCode` 该不该传，取决于 `beType`

- `beType=1`（到店自取）：返回的门店**没有** `beCode`，后续调用**不能**传（传了报错）
- `beType=5`（得来速）：**有** `beCode`，后续**必须**传

文档在描述里写了，但 schema 的 `required` 里没体现。**照着 `required` 写代码就会踩。**

### 坑 4：营养数据是 CSV 纯文本，而且名字对不齐

`list-nutrition-foods` 返回的 `data` 是 6016 个字符的**字符串**：

```
[160]{productName,nutritionDescription,energyKj,energyKcal,protein,fat,carbohydrate,sodium,calcium}:
  猪柳麦满分,null,1288,308,16,16,24,781,213
  中薯条,null,1210,289,4,12,38,165,18
```

而且名字有差异：套餐里叫「纯牛奶」，营养表里叫「纯牛奶（盒装）」。得做归一化后模糊匹配。

### 坑 5：缺营养数据按 0 计，会让错误结论排第一

4 个新品在营养表里查不到。我一开始偷懒按 0 填充——结果这些组合在**「低热量排行榜」上虚假登顶**，因为热量被算成了 0。

**这个错误非常隐蔽**：数字看着合理，排序看着正常，结论完全是错的。

改法是：缺数据的餐品直接从组合空间里剔除。代价是组合数从 154 降到 84，但结论可信。

**宁可少算，不能算错。**

### 坑 6（最阴）：多份槽位时，`roundList` 替换静默失效

这个我必须单独拉出来讲。

`calculate-price` 支持通过 `roundList` 自定义套餐组合：

```json
{
  "productCode": "9900005456",
  "quantity": 1,
  "roundList": [
    {"round": "1", "comboItemList": [{"code": "1440", "quantity": 1}]},
    {"round": "2", "comboItemList": [{"code": "4437", "quantity": 1}]},
    {"round": "3", "comboItemList": [{"code": "3050", "quantity": 1}]}
  ]
}
```

三件套上完美工作，三个极端组合全部命中预期价格。

于是我拿「全明星双人分享餐八件套」去试。这个套餐有 6 个 round，其中两个的 `quantity=2`（要选 2 份）。

返回结果：

| 传法 | 返回 price | 实际该是多少 |
|---|---|---|
| 只传 round 1-4 | 11700（117 元）| 49.90 |
| round 5/6 各传 1 个（quantity=1）| `data` 为空 | 49.90 |
| round 5/6 各传 1 个（quantity=2）| 11700 | 49.90 |
| round 5/6 各传 2 个不同商品 | 11800 | 49.90 |

**全部失败。而且最前面那个还带着 `success: true`、`code: 200`。**

从响应层面看，一切正常。你会以为算对了。

实际返回的 117 元是**原价**，不是套餐价。如果我直接采信，就会得出"八件套要 117 块"这种荒谬结论，然后把它当成"洞察"发出去。

## 三、真正的教训：status code 不等于业务正确

这 6 个坑里，前 5 个都会**报错**或者给出**明显异常**的值，你能立刻发现。

**第 6 个不会。**

它返回 HTTP 200、`success: true`、`code: 200`、字段齐全、结构正确——**唯一的问题是数字是错的**。

这在 AI 应用里是个致命模式。因为我们写 Agent 的时候，习惯性会做这种事：

```python
result = call_tool(...)
if result.get("success"):
    use(result["data"])   # ← 灾难就在这里
```

`success` 只代表**请求成功**，不代表**业务结果正确**。

任何自动化流程，都必须对返回值做**合理性校验**，而不是只看状态码。

我在项目里的改法是：检测到套餐含多份槽位（`quantity > 1`）时，**跳过核价，并显式标注"价格未经官方验证"**——而不是假装自己算对了。

三件套/四件套（全部 round `quantity=1`）不受影响，实测核价一致率 100%。

**知道自己哪里算不准，比算得准更重要。**

## 四、最后做出来的东西

- 枚举套餐全部合法组合
- 调官方 `calculate-price` 逐个真实核价（抽样一致率 100%）
- 输出价格-蛋白质的**帕累托前沿**，而不是"推荐一个搭配"
- 用**最大弦距法**求拐点，并给出**边际收益表**

最后一件事值得单说。

我最初用"离理想点欧氏距离最近"来找拐点。数学上完全正确——然后它在一个价格跨度 15 元的套餐里，**挑出了最贵的那个方案**。

算法对，结果荒谬。

改用最大弦距法之后，结论变成这样：

| 价格区间 | 多花 | 蛋白增加 | 每元换蛋白 |
|---|---|---|---|
| 32.00 → 33.00 | +1.00 | +7.0 | **7.00** |
| 34.50 → 36.00 | +1.50 | +2.0 | 1.33 |
| **36.00 → 44.50** | **+8.50** | **+2.0** | **0.24** |

**求解器的价值不是给答案，是给判断依据。** 它不只告诉你选什么，还告诉你再往上加钱会发生什么。
